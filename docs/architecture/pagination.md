# Pagination

Covers `src/lib/editor/extensions/pageBreaks.ts`, `columns.ts` and `columnsFlow.ts`, plus the
page geometry they share with `components/Editor.svelte` and `styles/editor.css`.

## Page break system (`pageBreaks.ts`)

A custom ProseMirror plugin that simulates paginated A4 layout entirely in CSS/DOM — no `<iframe>`, no actual page breaks in the document model. On every document change it:

1. Measures each top-level block's natural `offsetTop`/height (excluding existing spacers).
2. Calculates whether a block would overflow a page's content area.
3. Injects invisible `div[data-page-break-spacer]` widget decorations before blocks that need to move to the next page. A spacer inside a table is emitted as a borderless `<tr>` instead of a `<div>` (`spacerKind: 'table-row'`).
4. Sets `minHeight` on the `.tiptap` element so the visual page slots always exist.
5. Fires a `pm-pagecount` CustomEvent (bubbles to `Editor.svelte`) carrying `numPages`, `docHeight`, and `tableBreakBands`.

**Mirrored margins** ride the same per-block inset as a section's own side margins: `.tiptap`'s padding draws the odd page's pair, so a leaf landing on an even page is inset by `--user-margin-mirror` (right − left) one way and the other (`storage/pageMargins.ts`), and the header/footer band moves with it in `HeaderFooterLayer.svelte`. A block takes the inset of the page its first leaf starts on; a later part on a page of the same text width but other sides — a paragraph's lines past a break, a list item, a table row with its repeated header — is moved across with `position:relative` (`placeSides`, `.pb-shift`), as both word processors set each part at its own page's margins; a paragraph's last part is `inclusiveEnd`, so text typed at its end moves with it before the next pass. Out of the flow, so no pass measures it. Not moved: a part whose page changes the text width (that re-breaks lines), a too-tall row's cell continuation, and a straddling paragraph's own border or shading.

**Widow-orphan control:** `findLineSplit` picks the first line that overflows the page, then applies Word's/LibreOffice's rule (`MIN_KEPT_LINES` = 2, on by default in both via OOXML `w:widowControl`, so not configurable): fewer than two lines carrying over pulls one more down with them, and fewer than two staying behind cancels the split so the caller pushes the whole block. A leaf taller than one page slot passes `minLines: 1` — there the rule can't be satisfied and splitting is preferable to overflowing. A block with nothing above it on its page is never moved on (`page-opener-no-push`): that would leave the page empty, so it stays and overflows, as in both word processors — below a first-page footer taller than the body, the cover's first block was pushed to page 2. **Where a line ends:** a spacing above single puts its extra leading below each line, and LibreOffice lets the last line's share hang past the text area (probed at 200%: a 26.7-line area holds 27 lines, a 26.2-line one 26). `findLineSplit` measures a line's box bottom from the next line's glyph top less the block's lift, the same correction its carried line top takes; without it the editor kept one line fewer on pages whose grid ends near the margin. The split position comes from a binary search over `coordsAtPos`, which Chromium misreports inside an automatically hyphenated word (the second half's first letters sit on the line above), so a hit test at the line's edges moves it back to the line's true start. The spacer `div` then ends the line by force and drops the hyphen, which `pb-hyphen` draws again. **A split whose lines re-broke:** that forced end makes a split self-consistent — once the lines re-break under it (a font arriving after the pass that placed it, which `loadingdone` answers with a forced pass), a spacer left mid-line holds the words before it on a short line of their own, and every later pass measured that line as fitting. Probed: whether a paragraph at a page foot kept a lone "an" above its split depended on the run. `hideStaleLineSpacers` hides, for the pass's measurement, every line-split spacer whose line and the next word would fit together, so the pass splits the natural lines again.

**Images in a paragraph:** an as-character image is a line box like any other (`getLineRects`
measures `.image-node` alongside the text runs, and text sharing its line groups into it), so a
paragraph of stacked images breaks between them instead of overflowing the page. Only a *floated*
image keeps its paragraph atomic — a line-split spacer beside a float is dropped by ProseMirror.
A float hangs out of its paragraph's box, so the leaf's height reaches down to the lowest float
instead of stopping at `offsetHeight` — otherwise the paragraph measures as one text line and the
image walks off the page bottom. Text still wraps beside the float; only the push moves as a unit.
What the model can't see is how far that overhang moves the blocks *below* it: further than the
spacer it accounts for, so two layouts — or more, in a cycle — can each imply the next. `seenLayouts` remembers every layout placed since the last outside change, so a key seen again closes a cycle of any length; the pass settles on the cycle's layout the document prefers — the larger page count, then the larger key — placing the others in turn until its pass measures into the preferred one, which then stands (`cycleKept`): a pass measuring another member keeps it.
Keeping whichever layout came first made the page count depend on history: a
reloaded client or one a step behind in a shared session showed the other layout, and the count
of the layout it measured but did not place (one page apart, for good). Only an edit, another
client's edit in a shared session or a forced recalc forgets the memory (the TOC rewrites its
page numbers on every `pm-pagecount`, so resetting on any document change would leave nothing
to catch). A recalc that *answers* a pass carries `LAYOUT_ANSWER` and keeps it too: the field round (an index re-breaking its columns at its new top) and the tab stops. Counted as forced, an alphabetical index at the end of a 155-page manual erased the memory after every pass, and a three-layout cycle (a table a full-width frame squeezed to zero width, `frames.md`) paginated forever. The columns flow's recalc after a split or join is an answer too.
The dom run checks a lifted block's ping-pong from both of its layouts.
**Hard bound:** whatever feedback no guard knows, a pass runs only while fewer than `MAX_PASSES_PER_INPUT` (64) have run since the reader's last key, click, paste or drop, the last edit (a history-recorded change, which an open is; one appended to a layout-only write is layout) or another client's edit; no recalc, forced or answered, renews it, so the layout reached stands and the busy state clears. A file opens in about ten passes; the three-layout cycle above, unguarded, took 64 and ~15 s on 155 pages.

**Keeping blocks together** (`pageBreak.ts` attrs, both read from the direct property *and* the paragraph style): `keepNext` (`w:keepNext`, `fo:keep-with-next`) moves a block down when the successor's first `MIN_KEPT_LINES` no longer fit below it — one line is not enough, because widow-orphan control would carry the second one over and strand the block anyway (measured on the Math Guide: a heading left alone at the foot of page 8) — headings do that in Word and LibreOffice anyway, so `true` marks the others and `false` a heading whose style the file defines without it (probed: LibreOffice then leaves the heading at the foot of the page). A **run** of kept blocks goes down from its first block, whole, when it and the first lines of the block after it fit on one page — LibreOffice moved a lead-in line and its 18-item list (every item `w:keepNext`) to the next page and left 50mm empty below; a run longer than a page, or one ending in an atomic block taller than the page (a bibliography), keeps the one-level rule. An **index** is the exception among the atomic leaves: its rows are paragraphs in both word processors, so it starts wherever its title and first row fit (`indexHead`) and its own view breaks it between rows, and a heading kept with it needs only that much below it (probed: 30 lines, a heading, a 30- or 70-row index — LibreOffice keeps the heading on page 1 above 20 rows; pushing the index whole moved both to page 2, and under an empty heading left that one alone at the page foot). The row that opens the next page takes the gap plus its own space above as its margin, or it stands that much into the top margin. `keepLines` (`w:keepLines`, `fo:keep-together`) makes an otherwise splittable block paginate atomically, unless it is taller than the page slot, where Word splits it too. A table's `keepRows` (ODF `style:may-break-between-rows="false"`, no Word equivalent) is the same rule for a table: pageBreaks emits one atomic leaf for the whole wrapper instead of one per row, so a table with no room left moves whole (probed: LibreOffice leaves four lines of the page empty rather than break it, and splits the identical table when the attribute says `true`). A table's `keepNext` (ODF `fo:keep-with-next` on the table; a DOCX table whose every cell paragraph has `w:keepNext`, as LibreOffice's import reads it, and what the DOCX export writes back) makes the table one atomic leaf that keeps with the next block, so it joins a kept run: probed with 8 and 30 rows behind a kept caption, LibreOffice moves caption and table whole to the next page when the block after the table no longer fits, even where the table alone would have fit; with only the last row kept it splits the table as usual. List items in a cell count as cell paragraphs both ways. A kept table taller than a page starts on a fresh page and then breaks between rows in a Word document (`data-spacing-model='max'`; probed 70 rows after 30 lines: page 1 holds only the lines, rows 0–53 fill page 2; 108 rows: the last row does not follow the next block over), LibreOffice's `TableRowKeep` compatibility; the same table in a native ODT with `fo:keep-with-next` on the table splits right away. A kept caption before such a table LibreOffice moves alone to a page of its own; the editor leaves it above the break. Rows a **cell spans** are grouped the same way (`rowSpanGroups`): the spanning cell is one DOM box, so a break between them stretches it across the gap instead of splitting it — LibreOffice keeps such rows on one page too (probed). A group taller than the page cannot be kept whole and breaks per row as before.

**Line breaking:** `editor.css` overrides prosemirror-view's `white-space: break-spaces` back to `pre-wrap` on `.paper .tiptap`. Under `break-spaces` a line-end space may not hang into the margin and counts toward the line width, so lines break one word earlier than in Word/LibreOffice whenever a line reaches within a space width of the margin.

**A block's spacing is part of the block.** LibreOffice's paragraph frame includes the space
below it, so the fit test adds `leaf.spaceAfter` (and keep-with-next adds the successor's space
above too): a block whose text fits but whose spacing doesn't moves down whole. The **space
above** is then dropped at the page top where the *flow* had to break, as LibreOffice does — a
break the document asks for keeps it, and so does the document's first block. Probed against the
reference, page top at 20.01mm: a block with 6/20mm above lands at 26.00/40.01 after
`fo:break-before`, at 20.01 for either after an automatic break. Every chapter opening of a
book-style document is the manual case (measured: 4.23mm a page on one file) — unless the
document turns spacing at a page start off (`AddParaTableSpacingAtStart`, `storage/CLAUDE.md`),
where even a manual break loses it and `--pb-space-at-page-start` says so. `pageBreaks.ts` marks those
blocks with a `padding-top:0;margin-top:0` node decoration — geometrically, a leaf pushed by its
own spacer never measures as sitting at the page top, since `effectiveTop` excludes that push, so
the mark follows from the break it got. The value itself rides `--space-before`
(`storage/spacingModel.ts`); in the larger-of model a kept space is a margin outside the
leaf box, so the push tests subtract it (`kept`). Which breaks keep it is decided on import.

**A pass must not read its own last answer.** Dropping that space shortens the block, which moves
everything below it, which changes what sits at the *next* page top — so measuring the decorated
DOM made the two layouts imply each other, and the cycle guard froze whichever came first: the
same document opened at 59 or 65 pages from one load to the next. `collectLeaves` adds the dropped
space back (`spaceAbove`, and a running `cumulativeDropped` for the leaves below), so what it
measures is the document; the placement loop then takes the drop off `cumulativeShift` itself. The
rule is general — anything the pass decides has to be reconstructed out of the next pass's input.
Every leaf is therefore born through `naturalTopOf`: four of the six push sites (index, text box,
columns fragment, table row) once subtracted the spacers but not the dropped space, and a figure
frame below a chapter heading landed 16mm down its page.

**A justified line fits more in LibreOffice than in a browser:** it compresses inter-word spaces to
squeeze one more word on where CSS `text-align: justify` only stretches them, so a justified
paragraph may break one word earlier here (`tests/render-parity/README.md`).

**Per-section page margins.** Word's `w:pgMar` and ODF's page layout belong to the section,
not the document, so each section's `HfSet` carries its own `margins` (and `marginsFirst`
where an ODF master hands over to another with `style:next-style-name` — that layout governs
the section's first page, the successor's the rest). `Editor.svelte` publishes them as
`--pb-section-reach` (already the per-page content area) and `--pb-section-inset`
("leftFirst|rightFirst|leftRest|rightRest" px against the document's own side margins).
Vertically a spacer can only push down, so a section whose top margin is *smaller* than the
document's gets a **lifting** spacer — height 0 and a negative `margin-top` — on its first
block, and only where nothing was pushed onto that page ahead of it; `collectLeaves` counts
that margin into `cumulativeSpacerHeight` or the next pass measures its own answer.
Horizontally `.tiptap`'s padding draws one pair for every page, so the difference becomes a
`--sec-inset-left`/`-right` node decoration on the section's top-level blocks, added in by
everything that writes a block margin (`editor.css`, `indent.ts`, `styleSheet.ts`,
`tableView.ts`) and cleared on descendants so a nested indent can't count it twice. The page
a block lands on is read *after* its own spacer, so a forced break onto the section's second
page takes the "rest" pair. The rulers measure the caret's page (the edited zone's in a header or footer), its own sheet and margins, wherever the view has scrolled to, so they change only when the caret changes page; pages are read against `pageBoxes`, since they differ in height. The vertical ruler measures the same page: cm from its text area's top (an open zone's top while one is edited), the zones as bands; its page box comes from `pageBoxes`, so a scroll redraws nothing. Not carried: a frame's `COLUMN_WIDTH_CSS` stays document-wide.

**A node decoration does not survive its node being replaced** — a block's type or attrs changing is exactly that step — so the pass marks them (`blockDeco`) and re-cuts the spans `onRemove` reports lost (`repairDecos`). Without it the inset, a page-top margin, a note offset or a column fragment's height was gone until the next pass: a heading in a narrow section sat 164px left, as if the page had turned landscape. A block whose own bounds lie inside a deleted range was **replaced**, not restyled, and is not re-cut: opening a file replaces the whole document, and a column fragment's `height:934px` spread over the blocks now in its old range made the flow split a section into a fragment per page. A **spacer widget** sits on the boundary between two blocks, so replacing either one deletes its position too; `repairDecos` re-seats it (`spacerDeco`) wherever the mapping still puts it before a block. The next pass cannot restore a lost spacer on its own, since it finds the same placements and skips the dispatch: switching the document's language rewrote every block and left a document with only its first page break.

**Per-section paper.** A section's own format/orientation (`HfSet.format`/`.orientation`,
null = the document's) makes the pages differ in size, which a repeating background
cannot express — so the page grid is a **`PageGrid`** of height runs ("every page from
here on is this tall") instead of one cycle, and the sheets are one box per page
(`PageSheetLayer`). `placeLeaves` builds its own grid as each section's first page
becomes known, so a pass never measures its own last answer; it reports the runs, and
`Editor.svelte` publishes them as `--pb-page-runs` for every other consumer (the TOC, a
cross-reference, a page-anchored frame) plus `--pb-section-page` for the next pass.
`.paper` reserves the **widest** section's paper (`--pb-paper-width`) or a landscape page
would be cut at the sheet edge, and a narrower section splits the difference between its
two insets, on top of its own margins — so each page is **centred** in that box, as both
word processors draw one. Every per-page layer positions from the box's own `left`
(`PageSheetLayer`, `PageDecorLayer`, `LineNumberLayer`, `HeaderFooterLayer`); a run is
`fromPage|height|left` so `PageGrid.leftOf` hands that same edge to anything placed from
a page corner rather than in the flow (`image.ts`'s page-anchored frame), and
`tests/browser.mjs`'s `extractLayout` reads the runs to measure a word against its own
page. Every rule that writes a top-level block's horizontal margin has to add
`--sec-inset-left`/`-right` back in, or it draws that block at the sheet's edge instead
of its page's — `:is(h1…h10)` and `.toc` in `editor.css` both reset `margin` and did.

**The content band.** A run carries its section's four reaches too
(`fromPage|height|left|topFirst|topRest|bottomFirst|bottomRest`), so `PageGrid` answers
`contentTopOf`/`contentBottomOf` per page (a page in `--pb-page-reach` keeps its own pair: its zones' height with the page fields filled in) and `bandAt(vm, y)` per y — what the flow, the
index's rows and the column flow place against. `vm.top`/`vm.contentHeight` with a uniform
`vm.cycle` is wrong twice: those are **section 1's** reaches, so a section whose footer
stands in the text area keeps a row the flow would have pushed, and one page height
misplaces everything below a landscape section. `20-index-footer` is that document.

A section may **open with a table or an index**, so `pageBreak.ts` gives both node types
the `sectionBreak`/`breakBefore` pair; `walkTableRows` carries them onto the table's first
leaf and the index's own leaf reads them directly. Both node views build their own DOM and
never call `renderHTML`, so an attr the pagination reads off one has to be written there
too (`applyTableStyleAttr`, `TocView.applyFlow`).

**A list marker does not raise the line.** Both word processors measure a line as
`max(ascent) + max(descent + leading)` over its runs, and the bullet is a run of the
numbering level's own font — so a Word list whose level names `Symbol` draws its *first*
line ~3% taller than its continuation lines. The editor's marker is a `::before` in the
paragraph's font under a computed `line-height` (`--natural-line × --line-factor`), so
every line is the same height and a long bulleted document ends up a page or two short.
Closing it means per-run vertical metrics, and the target is not fixed: LibreOffice
substitutes a symbol font it does not have, so a Mac with Symbol and a Linux box on
OpenSymbol differ. Measured with `tests/render-parity`: 0.17 mm per bulleted first line,
caused by the level's **font**, not its glyph (a `•` in Symbol drifts, a Symbol glyph in
the text font does not).

**Tables across page breaks:** when a single continuous table box crosses a page boundary, the plugin reports `TableBreakBand`s (doc-px geometry). `Editor.svelte` renders an overlay (`.band-layer` inside `.paper`) that masks the table borders bleeding through the page margins and paints the dark page gap as one seam-free stripe. The mask is the table's own measured box and the stripe spans the two pages beside it, each edge line its own page's width: a page centred beside a wider landscape section is narrower than `.tiptap`, so the document's margins or the sheet's width would paint them into the dark surround. The mask starts where the closing page's text ends: its own section's reach, which the placement grid therefore carries (`PageGrid`'s own default is 2.54cm), less that page's footnotes — the table closes above them as in LibreOffice, and the notes paint over the mask (`z-index: 22`).

A break *between rows* instead closes the table on both sides of the gap: collapsed borders paint a shared edge only once, so the spacer `<tr>` would leave one fragment open. `splitLines` (`pageBreaks.ts`) resolves what LibreOffice draws there — the row separator the break falls on, or, where the rows carry none, the table's own box (probed: its **top** border closes the fragment, its **bottom** border opens the continuation) — and the spacer cell renders it as two absolutely positioned lines. Out of flow deliberately: a collapsed border on the spacer itself moves every row below it down by half its width.

**Only one view measures.** The plugin's closures (decorations, the placement keys, the
convergence budget) belong to the editor, not to a view, so a second view of the same
document would conflict with the first over them. `isSplitPane(view)` — the marker `Editor.svelte`
puts on a split pane's host — makes `view()` return an empty plugin view there: the pane
renders the decorations this pass produced, which is exact, since both panes are the same
width. Every **widget** decoration therefore builds its DOM in a `toDOM` function; a node
passed directly can only live in one of the two documents, and each view keeps taking it
back from the other.

**A pass keeps its spacers, and typing gets a pause.** The decoration set is mapped through
every transaction (`apply`) and each spacer widget carries a `key` naming what it draws, so
a pass that lands the same spacers keeps their DOM. Unmapped, an edit above them left every
widget one position off and the view rebuilt all of them — measured at the top of a
124-page document: 1.5 s a keystroke, 144 ms with the mapping. An edit's pass waits for `EDIT_IDLE_MS`
of quiet, so while the typing goes on only the keystroke itself costs; a forced recalc, a layout-only
write and an edit leaving the caret's block past its page's text area (`caretOverflows`, or a held Enter
keeps the caret off the page) never wait. Another client's edit in a session waits too, but at most
`REMOTE_MAX_MS` (1 s) after the first: a pass per arriving batch took the whole main thread on long
documents (`collab-soak.md`). One that moved what follows it (the content's bottom differs from the last pass's) is placed at once, in the frame that shows it: the reader is not typing, and waiting showed every page below jumping a line and back (up to 1.1 s at 142 pages). y-tiptap applies a batch as one step over every top-level block it touched, a whole table for a letter in a cell, so the decorations and the text-only test follow the changed ranges instead (`changedRanges`, `decoMapping`, also in `columnsFlow.ts` and `tabStops.ts`). Once quiet, the pass is skipped if every edit since the last one only put
text into or took text out of one textblock (`textOnlyBlock`: a paragraph or heading, inside lists at
most; a cell, note or frame reaches further) and the content's bottom is where the last pass left it. A
break inside it still forces the pass. The dom run checks the keystroke budget and a letter taken back.

**What a pass costs.** At the top of the dom run's 124-page document (Chromium) the measuring and placing take ~40 ms — `docPosBeforeElement` is the largest part, ProseMirror walks the parent's children for every position, so it is memoised per pass — and the decoration dispatch a few ms. Everything above that was the browser's, and three things each multiplied it: a **`:has()` left of a sibling combinator** under `.tiptap` makes Chromium restyle every element under it (67 000 with the squiggles, ~150 ms) on each child inserted there — a spacer, a split paragraph — so the band-clearing rule keys on an attribute `image.ts` writes; a **live `Range` per text node** in `getLineRects` — a Range is a document listener Chromium updates on every DOM removal, and a pass left hundreds behind until the next collection, so one Range is reused; and TipTap's Placeholder **hit-testing the viewport** twice per keystroke (`placeholder.ts` replaces it). The pass after a split went from 410 to 150 ms, the keystroke that splits from 219 to 50 ms; in a document of real words, where few squiggles split the text nodes, 47 and 18 ms.

**What a keystroke costs.** `node tests/perf/keystroke.mjs [100,250]` repeats `05-breaks` (177 and 442 pages, 2 200 and 5 500 textblocks), dispatches 40 single characters at its start, middle and end, and splits each dispatch by plugin hook (`apply`, `appendTransaction`, `filterTransaction`, `decorations`, a plugin view's `update`) and editor listener; `PERF_PROFILE=1` adds a CPU profile of the keys alone, which also sees the Svelte effects after the dispatch. Chromium, dev server, one machine under varying load (about ±1 ms between runs). Mean per key, before the fixes below:

| | 177 pages | 442 pages |
|---|---|---|
| whole dispatch | 5.2 ms | 14.4 ms |
| pageBreaks view (`caretOverflows`: its `offsetTop` forces the layout) | 1.5 | 3.4 |
| trackChanges author colours (walks for authors, revisions, gone blocks) | 0.8 | 1.7 |
| imageLine `apply` / notes sync (four walks) / pageBreak sweep | 0.4 / 0.3 / 0.2 | 0.8 / 0.7 / 0.6 |
| rest of the view update: ProseMirror, mostly `DecorationSet.forChild` | ~0.8 | ~5 |

Outside the dispatch the status bar's word count re-read the whole text every 300 ms of typing (~15 ms at 442 pages) and every review layer walked the revisions again. Now the revisions are kept per doc and a document without changes stays known as such (`addsReview`), the image-line decorations are mapped (`mapImageLines`), the break sweep reads the changed range, the notes sync skips a document without notes (`noteless`) and the word count adds up per block: the dispatch is 4.0 and 11.6 ms (median 3.7–3.9 and 11.5–11.6, p90 4.4–4.6 and 12.3–12.9). Left alone: the forced layout (in the next frame it costs the same), ProseMirror's decoration lookup, and the pass after an Enter (~0.55 s at 177 pages, ~1 s at 442). A walk taken out mostly moves its cost to the next one, which then meets the document cold: ranging the indent sweep left the total unchanged, so `indent.ts`, `bibliographyEntry.ts`, `caption.ts` and the navigator's bookmarks still walk.

**A pass tells the document only what changed.** `pm-pagecount` is announced where the numbers on it — page count, document height, the section start pages, the placements, the table bands — differ from the last announcement. Every reader re-reads the whole document from the event (the index resolves each row's page, the header band its geometry, every cross-reference its number) and writes back what it found, which is a document change, which is another pass: a pass that lands what the last one did would start the round again. Opening a 460-page document ran five rounds of that where four answer everything.

**The fields of one answer read together.** Every field that resolves against the settled
layout — each index's page numbers, every cross-reference — registers with
`scheduleFieldRound(view, owner, read)` (`pageBreaks.ts`) instead of scheduling a frame of
its own. The round reads the page grid once and hands it to every reader — they all resolve
against the same one — and runs every reader's measurement first and only then their writes, since
a write between two measurements makes the browser lay the whole document out again; a
write may return one more phase (the index reads back where its rows now fall), run after
every other write. Their cached results — the index `entries`, a reference's `text` — ride
**one** transaction, a dispatch of its own costing a view update over the whole document:
that alone was 55 ms per index on a 460-page file.

**Layout constants** (must stay in sync between `pageBreaks.ts`, `Editor.svelte`, and `editor.css`):
- `PAGE_HEIGHT = 1123px` (A4 portrait), `PAGE_GAP = 20px`, `CYCLE = PAGE_HEIGHT + PAGE_GAP = 1143px`.
- Page height/width and margins are read **live** from CSS custom properties (`--user-page-height`, `--user-page-width`, `--user-margin-*`) so orientation/margin changes don't require new constants. `Editor.svelte` places a y on a page against its `pageBoxes` (`pageAtY`), which follow each section's paper.
- A margin/orientation change dispatches an empty `FORCE_PAGE_RECALC` meta-transaction (deferred via `requestAnimationFrame`, outside the Svelte effect flush, to avoid re-entrant binding updates) to trigger a re-paginate. The tab pass (`tabStops.ts`) dispatches its first layout unconditionally, which forces one more pass after a load. Without that pass, WebKit spent ~9s rendering the first spell-check highlights of a long document (probed in `test:dom`; neither a forced reflow nor a frame's delay before the check helped, cause unknown).

## Multi-column sections (`columns.ts` + `columnsFlow.ts`)

- **`columns.ts`** (`Columns`) + **`columnsFlow.ts`** (`ColumnsFlow`) — multi-column (newspaper) layout with **cross-page flow** and **Word's sequential fill order**: column 1 fills to the page bottom, then column 2, then the next page — via per-fragment node decorations carrying `height:…;column-fill:auto` (full page slot for fragments with a continuation; content height + `OPEN_HEIGHT_SLACK_PX` for the open last fragment of a document-final chain **while the caret is in it** (`writingEnd`), so typing grows column 1 first without one-frame flashes into column 2 and balances on leaving, as the saved file shows). A chain followed by real content — another section counts — keeps its last fragment undecorated → CSS `column-fill: balance` (Word balances the end of a continuous section) — which only works because the paragraph mark's `::after` is `position: static` inside `.columns-node` (`editor.css`): the absolutely-positioned mark made Chromium give up balancing entirely and stack every block into column 1 (probed; a list's absolute `::before` markers do not trigger this). Because the box height is the plugin's own decoration, overflow/join decisions use content-based estimates (`contentHeightPx` = block rects + collapsed margins), not the rendered height. A section is a block region (`content: '(paragraph|heading|bulletList|orderedList|table)+'`) rendered as CSS multi-column (`column-count`/`column-gap` inline via `renderHTML`; no NodeView, no visual affordance — it must read as plain flowing text, so NOT isolating/selectable: selection, Backspace, and joins cross its boundary). Attrs: `count` (2–3) and `gapCm` (default `DEFAULT_COLUMN_GAP_CM` 0.5, clamp 0–5). Own group like textBox (Document is `'(block | textBox | columns)+'`). **Chain model:** the document may hold a section as several *adjacent equal-attr fragments* — the user-visible section is the maximal run (`columnsChain`); commands, export, and import all treat a chain as one section. **Cross-page flow (`columnsFlow.ts`):** a rAF layout pass (mirroring pageBreaks' geometry via the exported `readVerticalMargins`) keeps the fragmentation in sync with the page grid — an overflowing fragment is **split** at a block boundary so the maximal prefix fills its page (estimate = the flow poured into one column / count — `flowSpans`, block rects plus collapsed margins, the same measure the overflow test uses: counted by rects alone, one block too many stays and moves down a pass at a time), and a fragment with room **joins** the adjacent continuation back (the split pass then re-splits at the right point). A pass fixes every boundary it can judge, first to last (`MAX_FLOW_OPS`): after an op only the op's own fragment and chained continuations are judged — a continuation lands at a page top, so a full page is its room wherever it renders at that moment — and any other fragment waits for the next pass, so a multi-page section pages in one pass. Every op is `addToHistory: false` (layout-only; undo of user edits just re-flows) — **but prosemirror-history rebases its own steps over that op**, so an undo reaching back past one can leave a wrap standing that nothing can undo; `tests/monkey/` counts the flow's ops (`columnsFlowTx`) and leaves the history unchecked for such a run rather than assert a ceiling the design carries, composition-guarded, pass-budgeted (`MAX_FLOW_PASSES`, reset per external change — not by the tab-stop pass's recalc, which answers every flow op, so a join/split pair at one boundary restarted the budget forever). **pageBreaks.ts cooperation:** a `.columns-node` leaf carries `columnsFragment` (first-block fit estimate, `headFitPx` in columns.ts: two lines of a paragraph or the first row of a table, which the flow can cut, else the block's column share); on bottom overflow pageBreaks *waits for the flow* when that head fits the remaining space — the flow then splits between blocks or inside the first one, so a section below another starts mid-page as in LibreOffice — pushes it whole when mid-page (even taller-than-page), and at a page top does nothing (`columns-line-split-pending` — pushing a page-tall fragment would repeat the overflow on every following page). Both sides use the shared `COLUMNS_FIT_MARGIN_PX` for the first-block fit test — differing thresholds make split/push/join cycle at the boundary; the flow's join `HYSTERESIS_PX` must exceed the estimate error for the same reason — which a partial pull's estimate cannot promise (measured under CPU load: a head estimated at 37px costing 1266px, four boundaries joining and re-splitting for as long as the budget lasted, ~1s per op, which froze the main thread for a minute). A boundary the current budget **split** at is therefore never joined back (`splitAt`, the join position being `split` + 1), cleared with the budget on the next external change. The **overflow** test carries the same kind of headroom (`SAFETY_PX`): the estimate averages the flow over the columns, but a decorated column ends on a whole line, so a fragment measuring exactly its slot spills once the decoration pins the height — without it the flow reads its own last answer, measuring "fits" undecorated and "overflows" decorated forever. Every split or join therefore also clears the decoration cache key (`dispatchFlow`): ProseMirror drops node decorations whose node was replaced, and a stale key leaves the fragment at its balanced height instead of its page slot. **Page boundaries cut mid-paragraph at line boundaries** (`splitParagraphInBlock`): the flow measures a paragraph's rendered lines (`groupLines` — document-order rects banded by *overlap*: a rect joins the line it overlaps by half the taller of the two, so a raised run like a verse number is no line of its own and no outsized rect swallows the line below it), converts the page's leftover content budget into a line count by summing the **real** top-to-top advances (`linesWithin` — a line carrying a raised run is taller than the rest, so one median advance for all of them runs ~15% short; the median stands in only where the tops reset at a column break), finds the boundary text position by probing **both** edges of the line (all its rects, `groupLines`) and keeping the earlier position inside the paragraph (`lineStartPos` — on a right-to-left line the logical start is the right edge, and `left + 1` alone keeps a word too many, which costs one split pass per line; the engines list a line's rects left to right, so a right-to-left line's first rect can be the space hanging past its end, where a probe hits nothing of the paragraph and the cut fell back to the block boundary), and does a depth-2 `tr.split` whose second part carries the layout-internal **`joinPrev`** paragraph attr (a global attr minted by the Columns extension; never rendered/parsed, `keepOnSplit: false`). Used in two places: a paragraph taller than the whole page slot (`force` — at least one line stays), and the **boundary block** after `k` whole blocks fit (leftover room ≥ `MIN_TAIL_LINES` — so the last column of a page is filled instead of pushing the next paragraph out whole); the join side mirrors it by pulling a multi-line paragraph head at ~two line rows of room (partial pull; the re-split hands the excess back). A live per-fragment analysis is exposed via `getColumnsFlowDebug` and included in the dev Debug dump (`columnsFlow` key). pageBreaks skips the empty trailing paragraph after a document-final chain (`trailing-empty-after-columns`) so a sequential-fill box reaching the page bottom doesn't mint a phantom page. A **table** is cut the same way between two rows (`splitTableInBlock`), its second part a `joinPrev` table: rows are whole boxes (`.columns-node tr { break-inside: avoid }`, and its wrapper is no scroll container there, which no engine breaks across columns), so `rowsWithin` places them column by column exactly, opening the next column for a row that does not fit, and the overflow test of a fragment ending in a table uses the same placement instead of the averaged flow; a cut never crosses a row span (`rowBoundaryFree`), and `canSplit` is bypassed, since it refuses any split inside an isolating table. The table style's re-banding skips both parts, whose cells keep the paint of the whole table; a repeated header row is not drawn atop the continuation. LibreOffice reading a `.docx` draws a table that crosses a page in a continuous columns section in one column on the next page — its own `.docx` of the same document does the same (probed). Joins reverse it: a fragment join uses depth 2 when the continuation head is a joinPrev paragraph or table (needing only ~one line row of space), and a stray joinPrev paragraph *inside* a fragment merges into its predecessor immediately. A joinPrev part an edit leaves where no file can join it — after a block of another type, at the head of a fragment whose section has other columns (its gap or count changed under it), or outside any section — is a block of its own from then on (`strandedJoins`, an `appendTransaction` riding the edit): both exporters coalesce only equal-attr fragments, so the editor would hold one table the files hold as two. `mergeJoinedBlocks` (columns.ts) restores whole paragraphs on unwrap/absorb; `mergeJoinedParagraphsJson` (export/odt.ts, shared with docx.ts) does the same before serializing, so files always hold the original single paragraph. **Enter in an empty block** is bound by the Columns extension (`addKeyboardShortcuts`): the base chain's `liftEmptyBlock` would lift the block out of the section, or split the fragment mid-run, so the caret left column 1 for the page below instead of moving on to column 2. Inside a section it only splits the block; a list keeps its own escape (the guard fires only where the block's parent is the columns node). Commands: `setColumns(n)` — a **selection** gives its blocks n columns (1 takes them out) and every section it touches splits around them, keeping its own count; equal neighbours regroup into one section, and a box or index taking columns fails the command (`applyToSelection`); a bare cursor in a section: 1 unwraps the whole chain / 2–3 update it; elsewhere, the **whole document** gets columns (Word behavior; wrappable runs around boxes and indexes become one section each) — and `setColumnGap(g)` (chain-wide); helper `findColumns`. UI: a Columns dropdown in `ToolbarExpanded.svelte` (1/2/3 buttons + gap input, tick-derived active state). `trailingNode.ts` appends a paragraph after a trailing section. **ODF**: exported via the textBox-style sentinel hoist (`replaceColumns`/`applyColumns`, U+E009) as `<text:section>` + a minted section style with `<style:columns fo:column-count fo:column-gap>` — adjacent equal-attr fragments **coalesce into one section**; import resolves via `StyleResolver.sectionColumns` (gap also derived from per-`style:column` indents), wraps runs of allowed blocks (`pushColumnRuns`), moves boxes out with a warning (columns nodes from inner sections pass through silently), clamps >3 columns (the flow re-fragments after load); Word-style **page-layout columns** (`<style:columns>` in `style:page-layout-properties`, no `text:section`) are read via `StyleResolver.pageColumns` and wrap the whole body the same way. **DOCX**: full support — export splits the body into multiple `docx`-lib sections (`bodyGroups`; continuous breaks, `w:cols` with gap in twips, page geometry + fresh header/footer refs per sectPr, fragments coalesced); import groups body children on mid-body `pPr>sectPr` paragraphs (`splitBodySections`, empty markers dropped) and wraps groups whose sectPr has `w:cols w:num>1` — covering whole-document multi-column files via the body-final sectPr. A section whose own `w:type` is a page-starting break (nextPage/oddPage/evenPage, or absent = the default; `sectionStartsNewPage`, not `continuous`/`nextColumn`) tags its first block with `breakBefore:'page'` so the section starts on a new page like Word. A section whose **first block breaks the page** (an ODF `fo:break-before` there, or a DOCX page-break run ending the section before, which `breakCarry` hands across the section boundary) is pushed as a whole (`forceBreakBefore` on the fragment leaf), and keeps that block's space above, less the space below the block before it, as `padding-top` on the section (`sectionTops`) — so both columns start level below it, as in LibreOffice; `columnsFlow` takes the padding off the room it fills. The break still holds only as a section's first block; one further in is dropped (see `withoutPageBreaks`).
