# desktop/

Electron shell around `../dist`. Its own npm project, so the web app's install and CI never fetch Electron.
`npm start` runs it on a fresh build, `npm run dist` writes installers to `release/`, `npm test` is the smoke test (`APP=<binary>` for a packaged app).

- The app runs on the fixed secure origin `app://edentext`, where Chromium's File System Access API and `queryLocalFonts` work, so `saveFile.ts` and `recentFiles.ts` take their Chromium path unchanged. `main.mjs`'s permission handlers grant the page these (`fileSystem`, `local-fonts`) and the clipboard, and refuse everything else.
- File associations (`fileAssociations`, odt/ott/docx/dotx): a document arrives as a path (argument on Windows/Linux, also via `second-instance`; `open-file` on macOS), which opens a window holding it. `preload.cjs` is the only bridge — take the window's file, read and write — and `main.mjs` serves only paths the system handed over, kept in `opened-files.json` in the user data folder so recent entries reopen after a restart. Writes go through a temporary file. The page wraps a path in `storage/desktopFiles.ts`'s handle.
- `main.mjs` covers only what a browser does around the page: `http(s)`, `mailto` and `tel` links go to the system, navigation off the origin (a dropped file) is blocked, `will-prevent-unload` turns the page's silent `beforeunload` block into a discard dialog, and fields and selections get the cut/copy/paste menu with spelling suggestions that Electron leaves out.
- Vector PDF skips the print dialog: the page hands its print HTML to `printToPdf`, `main.mjs` serves it at `app://edentext/__print/<id>` (so fonts and pictures resolve) in a hidden window and returns `printToPDF`'s bytes; the page saves them with its own save picker. That response carries its own policy with `script-src 'none'`; the app page has the build's `<meta>` policy (`docs/architecture/embed.md`).
- One process only: a second process on the same profile loses its localStorage writes, so a second launch opens another window, the desktop's new browser tab.
- `window.prompt()` does not exist in Electron; the app asks through `askText()` (`src/lib/components/PromptDialog.svelte`).
- The service worker cannot register on `app://`; `src/main.ts` already ignores that error.
- Version and metadata come from the root `package.json` (`electron-builder.config.cjs`). The `desktop` job in `.github/workflows/release.yml` builds unsigned installers per platform and uploads them to the tag's release; it repacks the AppImage with appimagetool to embed update information and publish a `.zsync` for AppImageUpdate.
- Flatpak: `flatpak/` holds the desktop entry and AppStream metainfo, packed into the Linux `tar.gz` under `flatpak/` (in the root, appimagetool would take that desktop entry) (the release fills in version and date), and the Flathub submission manifest, which repackages that `tar.gz` and runs it through `zypak-wrapper`. Under `FLATPAK_ID` the update check stays silent; the profile lives in `~/.var/app/io.github.stffnb.edentext`, apart from the AppImage's.
- The macOS `icon.png` is rendered from `icon.svg` (the favicon plant on a white tile in the macOS icon grid); Windows and Linux use the free-standing `public/icon-512.png`. Render with `rsvg-convert -w 1024 -h 1024 icon.svg -o icon.png`.
- A packaged app asks GitHub for the latest release at start and offers its page when it is newer, unless that version was skipped (`skipped-version` in the user data folder); no auto-update, since an unsigned macOS app cannot install one.
- The native dialogs (discard, update) and the macOS menu take their text from `TEXT`, one entry per app locale, picked by the system language the way `resolveBrowserLocale` maps it. Windows and Linux get no menu: the ribbon has every command.
