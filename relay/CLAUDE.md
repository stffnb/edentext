# relay/

The collaboration relay (`docs/architecture/collab.md`). It is its own npm project and depends only on `ws`; the root keeps `ws` as a dev dependency for `tests/relay.test.ts`.
`npm run relay` in the root starts it on port 4390, and the Vite dev server proxies `/relay` to it (`RELAY_PORT` to change it).

- Protocol: a WebSocket on `/relay`. The first frame is text, `{"t":"hello","v":3,"room":"<id>","token":null,"id":n,"claim":"<secret>"}`. The room is a hash of the session key, never the key itself. The answer is `{"t":"welcome","peers":n,"frame":MAX_FRAME,"beat":BEAT_MS}`, or `{"t":"full"}` and close code 4001. A hello of another `v` gets `{"t":"version","v":3}` and close 4002; the app then says it does not match the server instead of dialling again, and takes a close 4000 before its welcome (a relay of version 1) the same way. Version 3 lets a client deflate a message inside the sealed envelope, which a version-2 app cannot read; the relay itself handles frames as before. A bad hello closes with 4000, none within 5 s with 4005 (a slow line, not an old relay), too many rooms with 4003. Everyone in a room gets `{"t":"peers","n":…}` when someone comes or goes.
- Binary frames are AES-GCM ciphertext, so the relay cannot read them. Text frames after the hello are dropped.
- Addressing: `id` is the client's random session id (1 to 2³²−1), `claim` a random secret (22–64 base64url characters) only the relay sees. The first hello with an id claims it for the room's lifetime: a later hello with the id and the same claim (the client dialling again) takes it over from its old socket, one with another claim closes with 4004, also after the client left, so nobody else can receive its frames or make the room announce it gone. A room remembers 256 ids; past that the oldest gone one is forgotten. Every binary frame starts with the receiver's id, 4 bytes big-endian in clear before the ciphertext, 0 for everyone. The relay puts the sender's id in its place and passes the frame to that client alone, or to all; a frame to an id not in the room is dropped. As no client can forge the sender, a receiver bounds unfinished messages per sender (`channel.ts`) and checks the sender a message names (`session.ts`); the relay learns nothing it did not know. When the id's current socket closes, the `peers` message says `"gone":id`, so the others drop that client at once instead of after awareness's 30 s.
- Every `beat` ms each client in a room gets `{"t":"beat"}`. Browsers cannot see WebSocket pings, so a client that hears nothing for three beats (15 s) drops the line as dead (half-open) and dials again; without `beat` in the welcome it never does. Back online or in view, a client whose line was silent for a beat waits a second for messages and otherwise dials again.
- `frame`, `beat`, `gone`, `slow`, `drained` and `got` are optional for a client: it ignores fields and messages it does not know, and against a relay without `frame` it splits at 256 kB. Clients split longer messages into sealed parts themselves (`src/lib/collab/channel.ts`), so the relay never sees a message, only frames.
- Backpressure: once a receiver holds more than `hold` (2 MiB) not yet sent, everyone else in its room gets `{"t":"slow","id":n}`, and `{"t":"drained","id":n}` once it is down to half or its line ended (the id may be back on a new one); a client then sends its pictures (the bulk lane, `channel.ts`) to that receiver, or to everyone, only in between, while edits, presence, pings and chat keep going. The relay keeps reading every sender, as it cannot tell a picture from a keystroke. Past `backlog` (8 MiB, four times the most a 49 MB picture join held in `collab-perf.md`'s bench, 2.5 MiB) it stops reading the sender that filled it until every other client holds less than half, a cap for a client that ignores `slow`; meanwhile that sender skips the ping check. A welcome is followed by a `slow` for each receiver still behind. Both messages are optional like `gone`: a client that ignores them meets the cap, so neither side needs a new protocol version.
- Receipts: each sender gets `{"t":"got","n":bytes}`, the binary bytes it sent since its welcome, at once once 32 kB more arrived and otherwise 20 ms after the last frame. A client measures its uplink by them and keeps only about 150 ms of pictures in flight (`channel.ts`); one that ignores them sends as before.
- The relay cannot tell readers from writers: both links of a session (`#collab=`, `#view=`) lead to one room, readers count toward `MAX_PEERS`, and only the clients check the writers' signatures.
- Nothing is stored: a room is a set of sockets in memory and disappears with its last client. No content and no room id is logged. What the relay still sees: addresses, times, frame sizes, how many share a room, and which random session id sends to which.
- Limits from the environment: `PORT`, `HOST`, `MAX_PEERS` (6, as measured in `docs/architecture/collab-soak.md`; 0 = none), `MAX_FRAME` (bytes per frame, 1 MiB, which a connection may hold half-received; larger closes with 1009; clients send at most 256 kB; `startRelay` keeps 16 MiB), `MAX_ROOMS`, `BEAT_MS` (5 s; 0 = none), `PING_MS` (5 s): a connection that misses a ping round is dropped, so a closed laptop or dead network leaves its room, `gone`, within two rounds.
  - `MAX_CONNS` (2000) and `MAX_CONNS_PER_IP` (20; 0 = none for either): open connections in all and per address, counted from the upgrade, before the hello too; past either an upgrade gets HTTP 429 and no WebSocket, which the app takes as an unreachable relay and dials again later. An IPv6 address counts by its /64.
  - `DIALS_PER_MIN` (60; 0 = none): upgrades per address and minute, as a bucket that holds as many; past it HTTP 429. Without it a client could dial again under ever new ids and start afresh at the session's limits per sender (`collab.md`, Limits).
  - `STUCK_MS` (30 s; 0 = never): a receiver holding more than `backlog` that long reads nothing and is dropped without a close handshake; its app sees the line end like any other and dials again.
  - `MAX_BUFFERED` (256 MiB; 0 = none): the bytes all receivers hold together; past it the one furthest behind is dropped the same way until the rest fit. Checked every second, often while a receiver is `slow`, and on each frame past `backlog`. A host's memory limit has to exceed it plus about `MAX_CONNS` × `MAX_FRAME` for frames on their way in.
  - `ALLOWED_ORIGINS` (none): pages allowed to connect, by their `Origin`, separated by commas or blanks, e.g. `https://docs.example.org app://edentext` (the desktop app). Another origin, or none, gets HTTP 403. Empty takes every one. It keeps other web pages' scripts out, not a client outside a browser, which sends any `Origin` it likes.
  - `TRUST_PROXY=1`: the address is the `X-Real-IP` header a proxy in front sets (the chart's nginx), not the socket's; without it the header is ignored, as anyone could send one.
- `/health` answers `ok`.
